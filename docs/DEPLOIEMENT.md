# Guide de déploiement — SIGBD

Public : équipe informatique du ministère de l'Économie et des Finances (DGBF / SSEBF).

Ce guide décrit la mise en production de SIGBD (API Node.js + client React) sur **MongoDB**
(support par défaut) ou sur **Oracle XE 21c** (support optionnel), conformément au cahier des
charges §13 (« Oracle ou MongoDB »). Le support se choisit avec `CORE_STORE`, `REFERENCE_STORE`
et `AUDIT_STORE` — voir le [README](../README.md), section « Choix de la base de données ».

Règles suivies dans ce document :

- chaque affirmation renvoie à un script ou à un fichier du dépôt (aucune fonctionnalité
  nouvelle n'est décrite) ;
- aucune commande n'est exécutée automatiquement ;
- aucun mot de passe réel : uniquement les placeholders déjà présents dans le dépôt ;
- les points **[À CONFIRMER]** attendent une réponse écrite de l'informatique du ministère.

## 1. Prérequis

### 1.1 Logiciels

| Prérequis | Détail | Référence |
| --- | --- | --- |
| Node.js ≥ 18 et npm | installation des dépendances | [README](../README.md), section Prérequis ; `npm run install:all` (racine) |
| MongoDB joignable | `MONGODB_URI`, défaut `mongodb://127.0.0.1:27017/sigbd` ; **obligatoire même en mode Oracle** (voir section 9) | `backend/.env.example`, `backend/src/config.js` |
| Oracle XE 21c | ou version fournie par le ministère **[À CONFIRMER]** ; en développement, conteneur `gvenzl/oracle-xe:21-slim` | `docker-compose.yml` |
| Client Oracle Node | `oracledb` en mode léger (thin) : aucun Instant Client à installer | `backend/src/db/oracle.js` |
| HTTPS | obligatoire en production (cookie de session `secure` dès `NODE_ENV=production`) | `backend/src/services/auth.js` |

Docker n'est requis que pour le démarrage local de MongoDB et d'Oracle
(`docker-compose.yml`, marqué « DÉVELOPPEMENT UNIQUEMENT »). En production, Oracle est
installé classiquement par le ministère ou un schéma existant est fourni : l'application ne
dépend que des variables `ORACLE_*` (`docker-compose.yml`, commentaire d'en-tête).

### 1.2 Réponses attendues de l'informatique du ministère

À obtenir par écrit avant toute mise en production (liste complète des points en attente) :

1. Système d'exploitation, gestionnaire de services et version de la distribution du serveur
   d'hébergement — **[À CONFIRMER]**.
2. Version exacte d'Oracle déployée (XE 21c ou autre), service, port et schéma applicatif
   mis à disposition — **[À CONFIRMER]**.
3. Politique de sauvegarde : fréquence, rétention, lieu de stockage, et responsabilité des
   sauvegardes physiques de la base Oracle — **[À CONFIRMER]**.
4. Terminaison HTTPS : reverse proxy disponible, nom de domaine, certificat, durée de validité
   — **[À CONFIRMER]**.

### 1.3 Reverse proxy et HTTPS

- `TRUST_PROXY=true` (défaut `false`) : le serveur fait confiance à **exactement un** reverse
  proxy placé devant lui (`app.set('trust proxy', 1)`), pour que l'adresse IP réelle figure au
  journal d'audit. Variables : `backend/src/config.js`, `backend/src/server.js`.
- Le client compilé (frontend/dist) interroge `/api` sur **le même domaine** (`frontend/src/api.js`) : le
  reverse proxy sert les fichiers de `frontend/dist` et transmet `/api` à l'API
  (README, section Déploiement).
- Le backend ne sert aucun fichier statique (aucun `express.static` dans `backend/src`) : sans
  reverse proxy, l'application n'est pas accessible.
- HTTPS est impératif en production : le cookie de session passe en `secure`
  (`backend/src/services/auth.js`), donc le navigateur ne le renverra jamais en HTTP.
- Configuration du proxy, nom de domaine et certificat : **[À CONFIRMER]** (point 4 ci-dessus).

## 2. Création de l'utilisateur et du schéma Oracle

### 2.1 Compte applicatif et privilèges

Aucune commande `GRANT` n'existe dans le dépôt : l'application se contente de se connecter
avec `ORACLE_USER`, `ORACLE_PASSWORD` et `ORACLE_CONNECT_STRING` (`backend/src/db/oracle.js`).

Privilèges **réellement utilisés** par le code actuel, à accorder par le DBA :

| Usage | Opérations émises par le code | Référence |
| --- | --- | --- |
| Connexion | session Oracle (compte `ORACLE_USER`) | `backend/src/db/oracle.js` |
| Création du schéma | `CREATE TABLE` (13 tables), `CREATE INDEX` (14 index) | `backend/db/oracle/001_schema.sql`, appliqué par `backend/src/scripts/oracle-schema.js` |
| Suppression du schéma (hors production) | `DROP TABLE` | `backend/db/oracle/000_drop.sql` ; options `--drop` / `--reset` refusées en production dans `oracle-schema.js` |
| Restauration d'une sauvegarde | `ALTER TABLE … MODIFY ID GENERATED BY DEFAULT AS IDENTITY (START WITH …)` | `backend/src/scripts/restore-oracle.js` |
| Exploitation quotidienne | `SELECT`, `INSERT`, `UPDATE`, `DELETE` sur les 13 tables | `backend/src/repositories/*Oracle.js` |

- Les privilèges exacts libellés par le DBA (et l'espace de tablespace / quota alloué au
  compte) sont à faire confirmer : **[À CONFIRMER]** — le dépôt ne contient aucune commande
  `GRANT` et n'impose aucun autre privilège système.
- Règles de nommage, contraintes et correspondance collection MongoDB → table Oracle :
  [SCHEMA_ORACLE.md](SCHEMA_ORACLE.md) (13 tables, 27 objets de création).

### 2.2 Pose du schéma

```bash
npm run db:oracle:schema
# équivalent : npm run oracle:schema --prefix backend
```

- Applique `backend/db/oracle/001_schema.sql` via `backend/src/scripts/oracle-schema.js`.
- Sortie attendue : `Schéma Oracle créé : 27 objets` ; échec : `Échec Oracle : <message>`
  (code de sortie 1). Les identifiants et le mot de passe n'apparaissent jamais dans la sortie.
- À exécuter **une seule fois** sur un schéma vierge : le script ne tolère pas les tables déjà
  présentes lors de la création (seule la table absente est ignorée lors d'une suppression).
- `--drop` et `--reset` sont refusés en production (`NODE_ENV=production`), avant toute
  connexion (`oracle-schema.js`, `analyserOptions`).
- Si le ministère fournit un schéma déjà créé : vérifier sa conformité avec
  [SCHEMA_ORACLE.md](SCHEMA_ORACLE.md) — **[À CONFIRMER]**.

## 3. Variables d'environnement de production

Toutes les variables ci-dessous sont lues par `backend/src/config.js`, sauf mention contraire.
`backend/.env.example` fournit le gabarit (copié vers `backend/.env` par `npm run setup`, qui
génère aussi un `JWT_SECRET` aléatoire de 96 caractères — `scripts/setup.mjs`).

### 3.1 Environnement et session

| Variable | Défaut | Rôle |
| --- | --- | --- |
| `NODE_ENV` | `development` | `development` \| `production` \| `test` ; en `production`, les refus de la section 3.4 s'appliquent |
| `PORT` | `4000` | Port d'écoute de l'API (`backend/src/server.js`) |
| `JWT_SECRET` | aucun (obligatoire) | Secret de signature JWT, **32 caractères minimum** ; aucun défaut utilisable en production |
| `SESSION_TIMEOUT_MINUTES` | `30` | Délai d'inactivité glissant en minutes |
| `TRUST_PROXY` | `false` | `true` / `1` : faire confiance à un unique reverse proxy (`backend/src/server.js`) |
| `CORS_ORIGIN` | absent | URL d'origine validée par `config.js` ; **aucun autre usage dans le code actuel** : API et client partagent le même domaine (`frontend/src/api.js`) |

### 3.2 Limites de débit et taille des requêtes

| Variable | Défaut | Rôle |
| --- | --- | --- |
| `JSON_BODY_LIMIT_KB` | `2048` | Taille maximale du corps JSON en KB (recensements et gabarits) |
| `RATE_LIMIT_WINDOW_MINUTES` | `15` | Fenêtre de limitation par utilisateur |
| `RATE_LIMIT_USER_MAX` | `1200` | Requêtes max par utilisateur et par fenêtre |
| `LOGIN_RATE_LIMIT_WINDOW_MINUTES` | `5` | Fenêtre de limitation de connexion |
| `LOGIN_RATE_LIMIT_MAX` | `60` | Tentatives de connexion max par IP et par fenêtre |

### 3.3 Stockage (MongoDB ou Oracle)

| Variable | Défaut | Rôle |
| --- | --- | --- |
| `MONGODB_URI` | aucun (obligatoire) | URI MongoDB ; exigée par `config.js` et utilisée au démarrage du serveur (`backend/src/server.js`) |
| `CORE_STORE` | `mongo` | Support du noyau : régions, structures, périodes, utilisateurs, modules, saisies, remarques |
| `REFERENCE_STORE` | `mongo` | Support des profils et des listes de référence |
| `AUDIT_STORE` | `mongo` | Support du journal d'audit |
| `ORACLE_USER` | vide | Utilisateur Oracle applicatif |
| `ORACLE_PASSWORD` | vide | Mot de passe Oracle (jamais journalisé ni renvoyé au client) |
| `ORACLE_CONNECT_STRING` | `127.0.0.1:1521/XEPDB1` | `hôte:port/service` |
| `ORACLE_POOL_MIN` | `1` | Taille minimale du pool (`backend/src/db/oracle.js`) |
| `ORACLE_POOL_MAX` | `10` | Taille maximale du pool |

À définir dans `backend/.env` pour que **tous** les scripts partagent les mêmes réglages. Les
variables `ORACLE_TEST_USER`, `ORACLE_TEST_PASSWORD` et `ORACLE_TEST_CONNECT_STRING` ne
servent que dans les tests (`NODE_ENV=test`) et n'ont pas lieu d'être en production.

### 3.4 Refus en production (backend/src/config.js)

Le serveur refuse de démarrer si :

- `JWT_SECRET` fait moins de 32 caractères, vaut `change-me-in-production-sigbd-2026` ou vaut
  la valeur d'exemple `votre-secret-jwt-d-au-moins-32-caracteres-ici` ;
- une variable `ORACLE_*` est définie ou qu'un des trois interrupteurs vaut `oracle`, sans
  `ORACLE_USER` ou sans `ORACLE_PASSWORD` ;
- `ORACLE_PASSWORD` vaut la valeur d'exemple `votre-mot-de-passe-oracle-ici`.

### 3.5 Variables des scripts (hors config.js)

| Variable | Défaut | Rôle | Référence |
| --- | --- | --- | --- |
| `SEED_DEMO_PASSWORD` | `Test@2026` hors production | Mot de passe des comptes de démo ; **requis** en production si le seed de démo est lancé | `backend/src/seed/demo.js` |
| `SEED_ALLOW_PRODUCTION` | absent | Autorise le seed de démonstration en production (à laisser vide) | `backend/src/seed/guard.js` |
| `INIT_DATA_DIR` | `backend/data/init` | Dossier des CSV `regions.csv` / `structures.csv` | `backend/src/seed/common.js`, `backend/src/scripts/init-structures.js` |
| `BACKUP_DIR` | `backups/` à la racine (droits 0700) | Dossier des sauvegardes | `backend/src/scripts/backup-common.js` |

### 3.6 Côté client

| Variable | Défaut | Rôle |
| --- | --- | --- |
| `VITE_API_URL` | `http://localhost:4000` | Déclarée dans `frontend/.env.example` ; le client compilé appelle `/api` sur le même domaine (`frontend/src/api.js`), cette variable ne sert qu'au développement |

## 4. Ordre de mise en service

Commandes à lancer depuis la racine du dépôt, dans l'ordre. Étape facultative si l'installation
est neuve (aucune donnée MongoDB à reprendre) : la migration (étape 4.3).

### 4.1 Installation et configuration

```bash
npm run install:all        # racine, backend, frontend (package.json)
npm run setup              # backend/.env + frontend/.env si absents, JWT_SECRET aléatoire
```

Puis éditez `backend/.env` : `NODE_ENV=production`, `JWT_SECRET` sur mesure, `MONGODB_URI`,
`TRUST_PROXY=true`, et les variables de la section 3.3.

### 4.2 Schéma Oracle (mode Oracle)

```bash
npm run db:oracle:ping     # vérifie la connexion : Oracle OK — version … — service …
npm run db:oracle:schema   # Schéma Oracle créé : 27 objets
```

Références : section 2 de ce document, [SCHEMA_ORACLE.md](SCHEMA_ORACLE.md).

### 4.3 Migration éventuelle depuis MongoDB (mode Oracle)

```bash
npm run db:migrate:oracle                                   # dry-run : plan, comptes, anomalies
npm run migrate:oracle --prefix backend -- --apply          # écrit puis vérifie ligne à ligne
```

- Source : MongoDB en **lecture seule** (`backend/src/scripts/migrer-mongo-oracle.js`) ; cible :
  les tables Oracle.
- **Ordre obligatoire** : tout juste après la pose du schéma et **avant** toute écriture de
  données (seed, structures, périodes, comptes) — la migration refuse une cible non vide
  (message `Cible Oracle non vide …`, code de sortie 1, rien n'est écrit).
- Pendant la migration, laissez `CORE_STORE`, `REFERENCE_STORE` et `AUDIT_STORE` à `mongo`
  (comportement validé, voir [SCHEMA_ORACLE.md](SCHEMA_ORACLE.md), section « Migration des
  données ») ; passez-les à `oracle` **après** le succès du `--apply`.
- Refus supplémentaires : références orphelines, doublons (codes, IM, libellés, clés de
  période et de saisie).
- Conséquences : les sessions JWT existantes deviennent invalides et les liens ou exports
  produits avant la migration pointent vers les anciens identifiants
  ([SCHEMA_ORACLE.md](SCHEMA_ORACLE.md), section « Conséquences après migration »).

### 4.4 Données de référence

```bash
npm run seed:ref --prefix backend
```

Crée (sans jamais supprimer ni modifier l'existant) les 5 profils, les 13 gabarits de modules,
les 32 ministères et les 223 EPN. Un second exécution affiche des comptes à 0 création
(`backend/src/seed/reference.js`, `backend/src/seed/common.js`). Sûr en production.

> En mode Oracle, ce script ouvre tout de même une connexion MongoDB
> (`backend/src/seed/reference.js`) avant d'écrire via les dépôts : `MONGODB_URI` doit rester
> joignable (voir section 9).

### 4.5 Régions et structures

```bash
npm run init:structures --prefix backend                                   # dry-run : rien n'est écrit
npm run init:structures --prefix backend -- --apply                        # écrit
```

- CSV d'entrée : `backend/data/init/regions.csv` et `backend/data/init/structures.csv`
  (`INIT_DATA_DIR` pour un autre dossier).
- En production, **toutes** les lignes doivent avoir `valide=oui` sinon le script s'arrête
  (l'option `--allow-unvalidated` est refusée en production) —
  `backend/src/scripts/init-structures.js`.
- Création des 3 structures centrales (SSEBF, DGBF, CELLULE_INFO) et des régions manquantes ;
  idempotent : un second passage crée 0 ligne.

### 4.6 Périodes de collecte

```bash
# vérification (dry-run)
npm run init:periodes --prefix backend -- --annee 2026 --echeance-mensuelle-jour 5 \
  --echeance-trimestrielle-jours 15 --premier-mois 10

# écriture (même commande + --apply)
npm run init:periodes --prefix backend -- --annee 2026 --echeance-mensuelle-jour 5 \
  --echeance-trimestrielle-jours 15 --premier-mois 10 --apply
```

- `--annee`, `--echeance-mensuelle-jour` et `--echeance-trimestrielle-jours` sont
  **obligatoires** et n'ont **pas** de valeur par défaut : les valeurs sont fixées par le
  SSEBF — **[À CONFIRMER]** côté métier (voir README, section « Générer les périodes »).
- `--premier-mois` limite la génération à partir du mois de mise en service.
- Le script ne modifie ni ne supprime jamais une période existante
  (`backend/src/scripts/init-periodes.js`).

### 4.7 Premier compte administrateur

```bash
NODE_ENV=production npm run create-admin --prefix backend
```

- Refusé hors production (`Ce script est destiné à la production uniquement.`,
  `backend/src/scripts/create-admin.js`).
- Demande IM, nom et prénom ; génère un mot de passe provisoire au format `Xxx-Xxx-Xxx`,
  affiché **une seule fois**, stocké sous forme de hachage avec `mustChangePassword=true` :
  l'utilisateur devra le changer à la première connexion.
- Aucun autre compte n'est créé par le script : les comptes réels sont saisis par l'Admin 1
  dans l'écran Utilisateurs (README, section « Initialiser une base réelle »).

### 4.8 Client et service

```bash
npm run build              # frontend/dist (frontend/vite.config.js)
npm start --prefix backend # API sur PORT
```

Le reverse proxy sert `frontend/dist` et route `/api` vers l'API (section 1.3). Le
gestionnaire de service (redémarrage automatique, logs) est à définir avec le ministère :
**[À CONFIRMER]** (point 1 de la section 1.2).

### 4.9 Tâche d'archivage (à programmer)

```bash
npm run archive --prefix backend
```

Passe en statut `archivee` les saisies `exportee` dont la période est terminée
(`backend/src/scripts/archive.js`). Aucune planification n'est intégrée au produit : la fréquence
relève de l'équipe systèmes (voir section 5.4).

## 5. Sauvegarde et restauration

### 5.1 Sauvegarde Oracle

```bash
npm run db:backup:oracle
# équivalent : npm run backup:oracle --prefix backend
```

- Fichier JSON des 13 tables : `backups/sigbd-oracle-<service>-<horodatage>Z.json`
  (`BACKUP_DIR` pour un autre dossier), **mode 0600**, dossier 0700
  (`backend/src/scripts/backup-oracle.js`, `backend/src/scripts/backup-common.js`).
- En-tête : format, version, date, service Oracle (jamais d'identifiant), nombre de lignes par
  table, somme de contrôle SHA-256 du contenu. Aucun mot de passe dans le fichier ni dans les
  journaux.
- Lecture seule sur la base : `SELECT` sans paramètre.

### 5.2 Vérification du fichier (sans connexion)

```bash
node backend/src/scripts/verify-backup-oracle.js [<fichier>]   # sans argument : le plus récent
```

Contrôle la somme de contrôle et les comptes de l'en-tête contre le nombre réel de lignes de
chaque table. Aucun identifiant ni mot de passe n'est lu (`backend/src/scripts/verify-backup-oracle.js`).
Ce script n'a **pas** de raccourci npm.

### 5.3 Restauration Oracle

```bash
npm run restore:oracle --prefix backend -- <fichier>            # dry-run : plan, aucune écriture
npm run restore:oracle --prefix backend -- <fichier> --apply    # écriture réelle
```

- Refus (code 1) : fichier absent ou incomplet, somme de contrôle incorrecte, base cible non
  vide, et `NODE_ENV=production` sans `--apply` explicite (décidé avant toute connexion) —
  `backend/src/scripts/restore-oracle.js`.
- Chemins des fichiers : les commandes `npm run … --prefix backend` s'exécutent dans `backend/`,
  un chemin relatif y est donc résolu depuis `backend/` (écrivez `../backups/<fichier>` pour le
  dossier `backups/` de la racine, ou un chemin absolu). Même règle pour toutes les commandes
  `npm run … --prefix backend` de ce document (sections 5.5 et 7) ;
  `node backend/src/scripts/…` lancé depuis la racine résout lui les chemins depuis la racine
  (section 5.2).
- Écriture : ids d'origine conservés, séquences réalignées au-dessus des ids restaurés, ordre
  des clés étrangères, **une seule transaction**. En cas d'erreur :
  `Transaction annulée : aucune donnée écrite. Ne retentez rien sans corriger la cause.`
- Succès : `Restauration terminée : les 13 comptes correspondent à la sauvegarde.`

### 5.4 Fréquence, rétention et protection des fichiers

- **Fréquence des sauvegardes Oracle, rétention et lieu de conservation : [À CONFIRMER]**
  (point 3 de la section 1.2). Le cahier des charges (NF-05) prévoit une sauvegarde quotidienne
  et un test de restauration chaque trimestre : à valider avec le ministère pour Oracle.
- **Test de restauration** : à exécuter sur une copie ou un schéma vierge, jamais directement
  sur la base de production (README, section « Sauvegarde et restauration »). Consigner le
  résultat dans la fiche de recette ([RECETTE.md](RECETTE.md), T-10).
- **Protection du fichier** : les sauvegardes contiennent les **hachages de mots de passe** et
  les données budgétaires ; elles sont créées en 0600 dans `backups/`, dossier **ignoré par
  git** (`.gitignore`). Le fichier ne doit jamais quitter le serveur sans chiffrement ni
  stockage sécurisé : **[À CONFIRMER]** avec le ministère (chiffrement au repos, support,
  accès).
- **Copie hors serveur** : indispensable (sinistre, perte du poste) — README, section
  « Sauvegarde et restauration ».
- **Sauvegardes physiques Oracle** (Data Pump, RMAN, réplication) : hors du code livré ; le
  produit ne les exécute pas. Leur responsabilité et leur fréquence sont à confirmer :
  **[À CONFIRMER]** (point 3 de la section 1.2).
- **Surveillance** : aucun mécanisme de notification n'est intégré (non-objectifs de la SPEC) :
  le journal de sortie de la tâche planifiée doit être contrôlé par l'équipe systèmes.

### 5.5 Équivalent MongoDB (support par défaut)

```bash
npm run backup --prefix backend                          # backups/sigbd-<base>-<horodatage>Z.archive.gz
npm run restore --prefix backend -- <fichier> --yes      # restauration
npm run backup:verify --prefix backend -- <fichier>      # vérification après restauration
```

Exemple de planification (documentation uniquement, rien n'est installé automatiquement) :
voir README, section « Sauvegarde et restauration ». Ces commandes exigent `mongodump` /
`mongorestore` (`backend/src/scripts/backup-common.js`).

## 7. Reprise après incident

### 7.1 Base Oracle

1. **Constater l'état** : dernière sauvegarde disponible dans `backups/` (`BACKUP_DIR`) et
   résultat de `node backend/src/scripts/verify-backup-oracle.js <fichier>` (fichier intact ?
   somme de contrôle correcte ?).
2. **Préparer une base vierge** : en production, `--drop` / `--reset` sont refusés
   (`oracle-schema.js`) → utiliser une base ou un schéma neuf, ou obtenir une base vidée par le
   DBA — **[À CONFIRMER]** avec le ministère (point 2 de la section 1.2). Recréer le schéma si
   besoin : `npm run db:oracle:schema`.
3. **Restaurer en deux temps** : `npm run restore:oracle --prefix backend -- <fichier>` (plan
   seul) puis, une fois le plan validé, la même commande avec `--apply`.
4. **Contrôler** : message `Restauration terminée : les 13 comptes correspondent à la
   sauvegarde.`, puis `npm run db:backup:oracle` pour repartir d'une sauvegarde à jour.
5. **En cas d'échec** : la transaction est annulée en entier, rien n'est écrit ; corriger la
   cause avant toute nouvelle tentative (message du script, section 5.3).
6. **Après une restauration** : les utilisateurs se reconnectent (identifiants et sessions),
   les exports produits avant l'incident restent valables dans la base restaurée.

### 7.2 Base MongoDB (support par défaut)

1. `npm run restore --prefix backend -- <fichier> --yes` sur une base de production **après**
   avoir arrêté l'API ;
2. `npm run backup:verify --prefix backend -- <fichier>` pour comparer les comptes ;
3. redémarrer l'API (`npm start --prefix backend`).

### 7.3 Cas particuliers

- **Migration MongoDB → Oracle** : si elle a été faite, les sessions JWT antérieures sont
  invalides et les anciens liens/exports sont caducs ([SCHEMA_ORACLE.md](SCHEMA_ORACLE.md),
  section « Conséquences après migration »). La migration ne peut pas être rejouée sur une
  cible déjà remplie.
- **Perte du journal d'audit** : impossible à reconstituer — le journal est *append-only*, sans
  route ni script de suppression (SPEC.md, section 6) ; c'est pourquoi la sauvegarde du support
  actif est indispensable.
- **Déclenchement manuel de l'archivage** : `npm run archive --prefix backend` (voir 4.9).

## 9. Limites connues

1. **MongoDB reste indispensable au démarrage.** Le serveur établit toujours une connexion
   MongoDB (`backend/src/server.js`) et sort en erreur s'il échoue ; `seed:ref` fait de même
   (`backend/src/seed/reference.js`). En conséquence, `MONGODB_URI` est **obligatoire** dans la
   configuration même si `CORE_STORE`, `REFERENCE_STORE` et `AUDIT_STORE` valent tous `oracle`
   (`backend/src/config.js`). Une instance MongoDB joignable doit donc rester disponible.
2. **Les scripts ne servent pas le client.** Aucun `express.static` dans `backend/src` : le
   reverse proxy doit distribuer `frontend/dist` et router `/api` (section 1.3).
3. **Aucune planification intégrée.** Sauvegardes, archivage et vérifications sont des
   commandes à déclencher (cron ou planificateur du ministère) : sections 4.9 et 5.
4. **Aucune notification.** Ni e-mail ni alerte (non-objectifs de la SPEC) : les échecs de
   sauvegarde ou d'archivage ne remontent que dans le journal de sortie de la tâche.
5. **Restauration Oracle sur base vide uniquement.** Le script refuse une base non vide, et
   `--drop` / `--reset` sont interdits en production : une base neuve doit être prévue pour
   chaque restauration complète (section 7.1).
6. **Changer de support après mise en service** suppose une migration vers une cible vide
   (`npm run db:migrate:oracle`) : les deux supports ne se complètent pas automatiquement.
7. **Seed de démonstration interdit en production** sans `SEED_ALLOW_PRODUCTION=true`
   (`backend/src/seed/guard.js`) : à ne pas activer, il supprime des données.
8. **Tests Oracle** : les blocs de tests Oracle ne s'exécutent que si `ORACLE_TEST_USER` et
   `ORACLE_TEST_PASSWORD` sont définis (`backend/tests/*.test.js`, `describe.skipIf`) ; les
   tests de sauvegarde MongoDB sont ignorés sans `mongodump`. Sans rapport avec la production,
   cela signale simplement que la couverture Oracle n'est vérifiée que sur un poste de test
   équipé ([RECETTE.md](RECETTE.md), section 5).
9. **Périodicité du Rapport d'activités** et règles d'échéance : valeurs à confirmer par le
   SSEBF avant la génération des périodes (README, sections « Périodicité » et « Générer les
   périodes »).
